# 10. PREP became a first-class concept

A server should ideally be brought to:

```text
money    = maxMoney
security = minSecurity
```

before serious exploitation.

This state became:

```text
READY
```

Current preparation thresholds in JIT4 are approximately:

```text
money >= 99.9% max
security <= min + 0.05
```

If the target is outside these constraints, it is considered cold/unprepared.

This led to the dedicated preparation path:

```text
harvest.js TARGET --prep-only
```

Example:

```text
run harvest.js phantasy --prep-only --tail
```

# 11. HWGW understanding

The fundamental production batch became:

```text
H
W1
G
W2
```

Meaning:

```text
Hack
Weaken #1
Grow
Weaken #2
```

The important realization was that **completion order**, not merely launch order, determines whether the batch remains stable.

Desired landing sequence:

```text
H
↓
W1
↓
G
↓
W2
```

This allows:

1. H to steal money,
2. W1 to remove hack security,
3. G to restore money,
4. W2 to remove grow security.

If timing is correct, the target returns to READY.

This became the core invariant of all later engines.

# 15. JIT v0.1

The next step was Just-In-Time scheduling.

Instead of firing a huge isolated wave and waiting for it to finish, batches became a continuous temporal pipeline.

Initial implementation:

```text

```

The first JIT experiments exposed an important problem:

```text

```

Example:

```text

```

This taught an important lesson:

> A scheduler must be evaluated by long-run stability, not by whether the first few batches look correct.

# 23. JIT4 portfolio optimizer

The first JIT4 multi-target approach was too naive.

It effectively behaved like:

```text
Target A gets most resources
Target B gets scraps
```

This could create absurd secondary lanes with very long periods and almost no useful contribution.

The architecture was therefore replaced by a global portfolio search.

Current `chooseEpoch()` now:

1. evaluates all viable targets,
2. ranks candidates,
3. preserves preferred/current targets,
4. builds a top candidate pool,
5. evaluates single-target portfolios,
6. evaluates two-target resource partitions,
7. uses actual resource consumption rather than nominal allocation,
8. rejects worthless secondary lanes,
9. chooses the portfolio with the highest total EV/s.

Relevant controls:

```text
portfolioTop   = 6
splitStep      = 5%
minLaneGain    = 3%
maxPeriodRatio = 10
```

A secondary target is not accepted merely because:

```text
--targets 2
```

exists.

`targets=2` means:

> use *up to* two lanes if the second lane materially increases total expected value.

This is intentional.

# 25. Telemetry correction

An important bug was discovered in JIT4 telemetry.

Originally performance was measured using:

```text
wallet delta
```

That was wrong.

The player may simultaneously receive or spend money from:

- crimes,
- jobs,
- purchases,
- upgrades,
- other systems.

This produced misleading results, including negative "income" despite successful hacking.

Telemetry was corrected to use:

```text
ns.getMoneySources()
    .sinceInstall
    .hacking
```

Therefore current production telemetry reports:

```text
hacking-income
REAL=$/s
```

while wallet delta is retained only as a secondary mixed metric.

This is a major measurement improvement.

# 26. Core-aware scheduling

CPU cores matter for:

```text
grow()
weaken()
```

Current allocation therefore prefers high-core hosts for G/W operations.

Hack allocation intentionally behaves differently.

A single multi-thread hack is preferred whenever possible because splitting hack threads across multiple processes creates multiple independent success rolls and changes variance relative to the planner's assumptions.

Current design:

```text
H:
    prefer one process
    prefer lower-core worker if possible

G/W:
    prefer strongest cores
```

This preserves valuable high-core capacity for operations that actually benefit from it.

# 27. JIT4 environment adaptation

JIT4 periodically checks the environment.

This exists because the world changes while the script is running:

```text
hacking level increases
home RAM increases
home cores increase
Formulas.exe appears
new opener appears
new server becomes rootable
worker fleet expands
```

Relevant timers:

```text
environment check ≈ 5 seconds
portfolio reevaluation ≈ 120 seconds
```

Target switching uses hysteresis:

```text
~18%
```

This prevents the optimizer from constantly switching targets because of tiny temporary score differences.

The intended property is:

> JIT4 should adapt to the machine it is currently running on rather than assuming the machine that existed when it started.

This property is extremely important for the upcoming Augmentation reset.

# 29. Drift and recovery philosophy

Drift is treated as a normal failure mode to detect and repair, not something to ignore.

Possible drift symptoms:

```text
money < expected threshold
security > expected threshold
batch execution failure
timing distortion
environment change
```

Recovery tools include:

```text
stopfarm.js
harvest.js --prep-only
JIT4 reconfiguration
```

Operational rule:

```text
If target state becomes uncertain:
STOP
→ PREP
→ VERIFY READY
→ restart production
```

Do not blindly continue a damaged pipeline.

# 41. Core lessons learned

## Lesson 1 — target state matters

Money and security are coupled state variables.

Never rank a target based solely on:

```text
maxMoney
hack chance
hack time
```

without considering recovery cost.

---

## Lesson 2 — completion order matters

For HWGW:

```text
H → W1 → G → W2
```

landing order is the invariant.

---

## Lesson 3 — theoretical EV is not real throughput

A model may predict:

```text
$79m/s
```

while actual measured income is:

```text
~$45m/s
```

Both numbers are useful, but they answer different questions.

Always measure actual hacking income.

---

## Lesson 4 — wallet delta is contaminated telemetry

Income from:

```text
crime
jobs
other systems
purchases
```

can distort wallet delta.

Use hacking-specific money sources to benchmark the hacking engine.

---

## Lesson 5 — RAM utilization is not the objective

This:

```text
RAM usage = 100%
```

does not imply:

```text
profit = maximum
```

The actual objective is:

```text
maximize stable real $/s
```

---

## Lesson 6 — cores are heterogeneous resources

Grow and weaken benefit from cores.

Hack does not use them in the same way.

Scheduling should understand this rather than treating every GB as identical.

---

## Lesson 7 — multi-target is an economic decision

Do not run two targets simply because there is enough RAM.

A second lane must increase total expected return enough to justify its complexity.

---

## Lesson 8 — short tests lie

A scheduler that survives:

```text
20 batches
```

is not proven.

Neither is:

```text
120 batches
```

The first serious confidence milestone became:

```text
1000/1000 verified
```

---

## Lesson 9 — every reset should make the next reset faster

Augmentation installation is not failure or loss.

It is the compounding mechanism of the game.

The correct comparison is not:

```text
Before reset: rich
After reset: poor
```

It is:

```text
Run N bootstrap time
vs
Run N+1 bootstrap time
```

The goal is for that time to collapse.

# 42. Bugs and failures worth remembering

Several failures directly shaped the current architecture.

### Deprecated/incompatible formatting APIs

Some older scripts broke on Bitburner v3.0.1 because of formatting API assumptions.

Lesson:

```text
do not blindly trust old community snippets
```

---

### Early sequential farming

Weak/grow/hack loops were stable but inefficient.

Lesson:

```text
sequential correctness is not sufficient for throughput
```

---

### Overly aggressive JIT timing

Very small gaps looked attractive but caused long-run drift.

Lesson:

```text
latency margin matters
```

---

### JIT2 false drift

Verification occurred while the next batch had temporarily changed the target.

Lesson:

```text
verification must understand pipeline state
```

---

### Naive multi-target JIT4

A second lane could consume scraps while contributing almost nothing.

Lesson:

```text
multi-target allocation must be solved globally
```

---

### Wallet-based telemetry

Crime and other cash flows polluted benchmarking.

Lesson:

```text
measure the subsystem directly
```

---

### `disableLog()` logging itself

A tiny but funny reminder:

```text
even observability code can create observability noise
```

Fixed in:

# 55. JIT4 next-generation roadmap

Current JIT4 is already strong, but several research directions remain.

## 55.1 Model calibration

Compare:

```text
projected EV/s
vs
REAL hacking $/s
```

and learn the systematic gap.

The optimizer should eventually optimize against observed performance rather than purely analytical estimates.

---

## 55.2 Adaptive timing

Instead of static candidate gaps:

```text
200
175
150
125
```

future versions could maintain empirical safety data per environment.

Example:

```text
150ms:
1000 batches
0 drift
REAL 47m/s

125ms:
400 batches
2 drift events
REAL 50m/s
```

Then choose based on measured risk-adjusted throughput.

---

## 55.3 Generalized portfolio scheduling

Current architecture searches up to two meaningful lanes.

Future system could solve:

```text
N targets
M worker pools
heterogeneous cores
variable periods
shared RAM
```

without combinatorial explosion.

Potential techniques:

```text
greedy marginal allocation
beam search
knapsack-like resource partitioning
incremental lane admission
```

Do not build this until two-lane optimization has enough empirical data.

---

## 55.4 Dynamic reserves

Current reserves:

```text
home   20%
remote  8%
```

Future system could reduce or increase these based on:

```text
scheduler stability
recent exec failures
worker fragmentation
active utility scripts
target count
```

---

## 55.5 Purchased-server awareness

Future JIT versions should treat purchased servers as first-class workers and evaluate cost per additional EV/s.
