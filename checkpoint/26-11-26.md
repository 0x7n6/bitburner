# 1. Executive summary

The major milestone achieved on 26 November 2026 was the successful completion of BitNode 1 and entry into BitNode 4.

The project entered BN4 with an existing, sophisticated hacking infrastructure developed throughout BN1.

However, the transition exposed a fundamental architectural weakness:

```text
7n8 OS was optimized for a mature economic environment,
but was not capable of recovering efficiently from
a minimum-resource BitNode reset.
```

The previous infrastructure assumed relatively abundant RAM, sufficient hacking skill, multiple port-opening programs, and access to advanced economic systems.

After entering BN4, those assumptions no longer held.

The system retained its source code but lost most of its operational resources.

JIT5 could no longer be treated as the universal starting engine.

This resulted in the introduction of a dedicated recovery engine:

```text
early.ts
```

The project subsequently evolved into:

```text
7n8 Adaptive OS
```

with the following engineering doctrine:

```text
The OS adapts to the environment.
The environment does not need to adapt to the OS.
```

The objective is no longer limited to optimizing hacking income.

The broader objective is to construct an operating system capable of:

- Recovering from a fresh BitNode or augmentation reset.
- Discovering available capabilities.
- Allocating limited resources.
- Generating initial capital.
- Expanding the rooted network.
- Automating player progression.
- Selecting an appropriate economic engine.
- Transitioning between engines safely.
- Recovering from execution failures.
- Managing the entire BitNode lifecycle.

# 8. Root cause analysis

The primary architectural problems were identified through direct repository inspection.

## 8.1 Missing recovery engine

The daemon originally assumed:

```typescript
const ENGINE = "jit5.ts";
```

When JIT5 could not be launched, the supervisor delayed and retried.

It did not have a lightweight fallback engine.

This created a potential recovery deadlock:

```text
Insufficient resources
    ↓
JIT5 cannot launch or operate efficiently
    ↓
No productive hacking income
    ↓
Insufficient capital for upgrades
    ↓
Resources remain insufficient
```

## 8.2 Premature share supervision

The original share manager used:

```text
Default reserve: 512 GB
Minimum configurable reserve: 128 GB
```

Starting home RAM was only 32 GB.

The manager could run, but its worker budget was effectively zero.

It consumed RAM without contributing meaningful production.

## 8.3 Premature progression allocation

The existing progression service primarily automated backdoors.

It did not yet automate the initial acquisition of money, hacking experience, programs, or infrastructure.

Its persistent RAM allocation competed with recovery and control-plane resources.

## 8.4 No automatic engine lifecycle

The OS lacked a complete state machine covering:

```text
Cold boot
Recovery
Resource expansion
Engine admission
Engine handoff
Production
Failure recovery
```

## 8.5 Silent admission failure

JIT5 launch failures caused by insufficient RAM were not sufficiently visible to the operator.

The daemon could repeatedly wait without clearly reporting the required and available RAM.

# 11. Part I — Cold Boot Recovery

Part I introduced a dedicated lightweight recovery controller:

```text
scripts/early.ts
```

Its purpose is to restore productive execution after a reset.

It is not intended to replace JIT5 as the mature production engine.

The recovery controller reuses existing worker scripts:

```text
h.ts
g.ts
w.ts
```

Approximate worker RAM costs based on official API costs:

| Worker | Operation |     RAM |
| ------ | --------- | ------: |
| h.ts   | Hack      | 1.70 GB |
| g.ts   | Grow      | 1.75 GB |
| w.ts   | Weaken    | 1.75 GB |

The original recovery algorithm:

```text
Discover rooted network
    ↓
Select an eligible target
    ↓
Inspect target security
    ↓
Inspect target money
    ↓
Select hack, grow, or weaken
    ↓
Calculate required threads
    ↓
Distribute threads across available remote servers
    ↓
Wait for wave completion
    ↓
Reevaluate environment
```

Only one operation type is executed in each wave.

This deliberately sacrifices advanced concurrency in favor of simplicity, predictability, and low resource requirements.

# 12. Early engine execution model

The basic operation priority is:

```text
1. Restore security.
2. Restore server money.
3. Hack when economically feasible.
```

If security is above its minimum threshold:

```text
WEAKEN
```

If target money is below 90% of maximum money:

```text
GROW
```

Otherwise:

```text
HACK
```

If hacking is not viable, the controller can use weaken operations to obtain hacking experience.

The default desired hack fraction is:

```text
10%
```

The recovery engine dynamically distributes threads according to the available RAM on rooted remote servers.

Home RAM is intentionally excluded from ordinary worker allocation to preserve the operating system and operator control.

This is an explicit architectural trade-off.

```text
Home:
Control plane and orchestration.

Remote network:
Execution capacity.
```

Future resource schedulers may use idle home RAM opportunistically, provided sufficient control and recovery headroom remains reserved.

# 20. Dynamic target selection

The new target scoring heuristic is based on:

```text
score =
    maximum money
    × hacking success probability
    × hack fraction per thread
    × readiness factor
    / hack duration
```

Where:

```text
readiness =
    0.5 + 0.5 × currentMoney / maximumMoney
```

with the readiness ratio constrained to a valid range.

The target selector filters for:

- Existing rooted servers.
- Accessible hacking requirements.
- Positive maximum money.
- Positive hack chance.
- Positive hack fraction.
- Finite and positive hacking duration.

The world daemon is excluded from automatic economic target selection.

This produces a rough expected-income-per-thread-per-second ranking.

It is not a complete HWGW throughput model.

Known limitations:

- Grow costs are not fully included.
- Weaken costs are not fully included.
- Target preparation duration is not fully modeled.
- Execution pool fragmentation is not incorporated into the score.
- Actual wall-clock revenue is not yet used as the primary target selection metric.
- CPU core differences are not fully modeled.

The eventual improvement should use empirical cycle economics rather than relying exclusively on a static hack-derived score.

# 21. Target selection hysteresis

The new selector attempts to avoid excessive target switching.

The current target is retained unless the challenger has approximately 1.5 times its score.

```text
Target switch threshold:
approximately +50% estimated score.
```

This is an engineering policy chosen to reduce unnecessary preparation costs and switching instability.

It has not yet been empirically optimized.

Future work should evaluate the relationship between:

```text
Switching cost
Preparation time
Expected revenue improvement
Remaining target lifetime
```

A target with higher theoretical income is not automatically a better operational target.

# 26. Supervisor-first shutdown

Part II-A updated the full shutdown procedure to terminate:

```text
bootstrap.ts
daemon.ts
```

before sweeping the remaining managed processes.

The purpose is to prevent supervisors from recreating services during shutdown.

The ordinary farm pause remains distinct from full OS shutdown.

```text
stp
    Farm pause.
    Daemon remains alive.

stp-rs
    Resume managed farming or bootstrap the daemon.

stp-os
    Stop bootstrap, daemon, and managed services.
```

The stock trader retains an independent lifecycle.

The OS must not automatically liquidate stock positions simply because farming is paused or stopped.

Trader operations remain controlled through:

```text
traderctl.ts start
traderctl.ts stop
traderctl.ts drain
traderctl.ts status
```

Full managed OS shutdown does not currently mean termination of every arbitrary process in the game.

# 28. FindV2 hardening

The initial `findV2.ts` implementation contained several issues.

## Dry-run side effects

Automatic rooting was originally performed before checking the dry-run flag.

Part II-A moved this mutation behind a dry-run guard.

## Incorrect terminal starting assumptions

The generated command chain now begins with:

```text
home
```

This avoids assuming that the player is already connected to home.

## Navigation ownership

FindV2 now checks whether `progression.ts` is running before performing active navigation.

The daemon also avoids starting progression while FindV2 is active.

This reduces navigation conflicts but does not constitute a complete global navigation lock.

## Protected world daemon completion

FindV2 no longer automatically backdoors:

```text
w0r1d_d43m0n
```

Automatic BitNode destruction must remain an explicit operator decision until controlled completion automation is intentionally designed.

## Root validation

The NUKE result is now checked before reporting successful rooting.

## Duplicate fallback prevention

Backdoor execution failures are handled separately to reduce the risk of repeating a backdoor operation through the DOM fallback.

## DOM fallback limitations

The fallback uses internal terminal React properties.

This is not a stable official Netscript API.

It should remain a compatibility fallback rather than the preferred execution path.

Part II-A implementation passed TypeScript validation, but individual FindV2 runtime paths still require regression testing.

# 61. Why blindly increasing aggressiveness is rejected

Historical JIT5 engineering established that process concurrency can become a system bottleneck.

Existing governor settings include:

```text
Planned PID capacity: approximately 6800
Soft PID ceiling: 8000
Hard PID ceiling: 9500
```

Historical experimental observations associated substantially higher process pressure, around 12,400 concurrent PIDs, with scheduler starvation.

These are empirical project values, not official universal Bitburner limits.

The following changes should not be made blindly:

```text
Increase take percentage.
Decrease batch gap.
Increase PID ceiling.
Increase concurrent target count.
```

Aggressiveness without scheduler efficiency may reduce actual wall-clock income.

The preferred direction is:

```text
More useful work per unit of computational resource.
```

## 76.1 Temporary API execution

The helpers include:

```text
getNsDataThroughFile()
runCommand()
waitForProcessToComplete()
```

Expensive API calls are isolated in temporary scripts.

This is commonly called RAM dodging by the community.

The actual API RAM cost is not eliminated. Instead, the cost
is allocated only while the corresponding process executes.

Proposed adaptation:

```text
Persistent supervisor
    ↓
Capability and RAM admission
    ↓
Typed temporary task
    ↓
Structured result
    ↓
Task exit and resource release
```

Prefer independently implemented typed task modules over
unrestricted dynamic script generation.

The inspected daemon contains periodic auxiliary tasks.

| Task | Interval |
|---|---:|
| TOR manager | 25 seconds |
| Program manager | 26 seconds |
| Contractor | 27 seconds |
| RAM manager | 30 seconds |

These are reference values, not mandatory 7n8 settings.

The important separation is task eligibility, interval, priority,
RAM requirement, execution lifetime, and retry policy.

## 76.3 Shared capital reserve

Alain coordinates expenditure through shared reserve policies.

7n8 OS should adopt a unified capital policy to prevent
independent services from competing blindly for money.

Examples:

- Trader spending cash reserved for Daedalus.
- Fleet purchases delaying critical home RAM upgrades.
- Infrastructure spending consuming augmentation capital.

## 76.4 Lifecycle progression

The autopilot tracks Daedalus eligibility, player capital,
hacking level, augmentations, faction membership, and resets.

This is directly relevant to Operation Singularity.

The objective is not simply to automate individual functions,
but to automate decisions about when those functions are useful.

## 76.5 Coding contracts

Contract discovery and solving are separated.

Coding contracts provide potential additional money or reputation
without relying exclusively on continuous HGW throughput.

Implement validated solvers and preserve limited contract attempts.

Do not submit unverified solutions automatically.

## 76.6 Economic modeling

The reference analyze-hack script considers operation duration,
RAM costs, security repair, and expected hacking revenue.

Adopt the principle of measuring the complete economic cycle,
rather than ranking targets solely by theoretical hack income.
