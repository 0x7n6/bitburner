# 1. Executive summary

The main research question from the 19 November checkpoint was:

> Can JIT5 retain its hot HWGW pipeline across adaptation windows so that end-to-end wall-clock income approaches hot pipeline income?

The answer is now:

```text
YES
```

The γ2 engine could produce approximately:

```text
~$5b/s
```

while hot.

But actual wall-clock hacking income was only roughly:

```text
~$60m–$90m/s
```

because every metric/adaptation epoch destroyed and rebuilt the pipeline.

Observed efficiency:

```text
wall / hot
≈ 1.5%
```

γ3 separated:

```text
pipeline lifetime
```

from:

```text
measurement-window lifetime
```

and eliminated ordinary epoch cold-starts.

Observed later:

```text
actual ≈ $4.94b/s
wall   ≈ $4.95b/s
```

and:

```text
actual ≈ $4.69b/s
wall   ≈ $4.69b/s
```

Therefore:

```text
hot pipeline throughput
≈
wall-clock economic throughput
```

during stable production.

This was the largest architectural performance improvement of the project so far.

`initRuntime()` reset:

```text

```

would not have solved the problem.

# 13. Multi-lane measurement bug

The old metric calculated:

```text
first hack across all lanes
→
last hack across all lanes
```

for measured portfolio throughput.

This was wrong when target action times differed significantly.

Example:

```text

```

The contradiction exposed a bad measurement window.

Fix:

```text
measure each lane independently
↓
calculate each lane's own hot duration
↓
sum lane measured rates
```

This corrected portfolio telemetry.

# 23. γ3.5 predictive concurrency

Current JIT5 generation:

```text
γ3.5 PREDICTIVE CONCURRENCY
```

Major idea:

> Do not wait until process pressure becomes a runtime emergency.

Estimate steady-state process concurrency during planning.

Approximate conceptual model:

```text
concurrent processes
≈
(H lifetime
 + W1 lifetime
 + G lifetime
 + W2 lifetime)
/
batch period
```

with safety correction.

Important discovery:

```text
take%
```

mostly changes:

```text
threads inside an action
```

while process pressure is dominated by:

```text
action lifetime
/
batch cadence
```

Therefore the correct response to excessive PID pressure is often:

```text
increase period
```

not:

```text
blindly reduce take
```
